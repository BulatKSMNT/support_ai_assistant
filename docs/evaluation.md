# Оценка качества

В `evaluation/questions.jsonl` — 18 проверочных вопросов по шести вымышленным документам и 4 вопроса вне их тематики. Это открытый синтетический smoke-набор для проверки работоспособности. Он не является независимым тестом на реальных обращениях и не доказывает качество промышленного внедрения.

`scripts/evaluate.py` отдельно проверяет BM25, векторный поиск и их объединение RRF. Измеряются доля найденных ожидаемых документов среди пяти фрагментов, MRR документов внутри этой выборки, доля пустых выдач для посторонних вопросов и HTTP-задержка p50/p95. Время первого прогрева модели включается в результаты. Нельзя сравнивать эти задержки как чистую производительность ранжирования: векторный поиск обращается к модели эмбеддингов.

```bash
uv run --no-sync python scripts/evaluate.py
# Для режима без моделей:
uv run --no-sync python scripts/evaluate.py --modes lexical
```

В основной конфигурации порог cosine similarity задан `RAG_MIN_VECTOR_SCORE=0.45`. Он не является универсальным порогом достаточности знаний. На другом корпусе/модели его нужно выбирать на отдельной валидационной выборке. BM25 использует словоформы русского и английского языков через stemming. RRF объединяет ранги; его score не является вероятностью правильного ответа.

При генерации гибридный контекст дополнительно ограничивается относительным порогом `RAG_CONTEXT_SCORE_RATIO=0.6`: слабосвязанные фрагменты не добавляются только ради заполнения top_k. Это особенно полезно, когда первые результаты подтверждены обоими видами поиска, а остальные — только одним. Порог выбран на учебном примере и может снижать полноту контекста; для нового корпуса его нужно валидировать. `/v1/search` возвращает исходное ранжирование, поэтому метрики поиска не измеряют автоматически качество отобранного контекста или ответа.

## Отдельно проверить ответы LLM

Для каждого ответа вручную отметить:

1. Отвечает ли он на вопрос.
2. Подтверждён ли каждый факт указанным фрагментом.
3. Не появились ли выдуманные сроки, цены, обещания или действия.
4. Перечислены ли действительно недостающие сведения.
5. Корректен ли отказ для вопроса без ответа в документах.

Сервер валидирует JSON, существование идентификаторов источников и наличие ссылок у каждого блока. Это структурная проверка; семантическую истинность фактов она не доказывает. Инструкции в документах передаются как недоверенный контекст; это не гарантия полной защиты от prompt injection.

Для первой версии добавлены два консервативных ограничения. Распознаваемые запросы актуальных цен, остатков, платежей и статусов получают отказ до вызова модели: источником этих данных должен стать API CRM. Числовые токены, которых нет в цитируемых документах или переданном контексте заявки, отклоняются с `unsupported_numeric_claim`. Это не полноценный фактчекинг: совпадение числа не подтверждает его смысл, числа прописью и произвольные перефразирования не покрываются. Ограничения следует развивать вместе с проверкой на реальных запросах.

## Для диплома

После появления реальных регламентов подготовить 80–150 вопросов с проверенными источниками. Отделить выборку для настройки поиска и закрытую тестовую часть. Добавить неоднозначные вопросы, устаревшие документы, вопросы без ответа и случаи с некорректными инструкциями в источниках. Сравнить поиск и качество ответов на одном разбиении; отдельно измерить время подготовки ответа менеджером.

Реранкер, закрытый тестовый набор и автоматическая оценка фактической корректности в первой версии не реализованы.
